# RAG-подсистема AI-юриста CargoTech — архитектура и план

> Кейс 4. AI-помощник юриста по претензионно-исковой работе (Каргософт / Marshall MTL, GigaChat).
> Документ описывает **только RAG-контур**: как индексируются документы и как из них извлекается контекст для генерации претензии. Генерация, guardrail-агент, триггеры просрочек, UI — вне scope этого документа (обозначены только точки стыковки).

---

## 1. Роль RAG в общем пайплайне

RAG — это «поставщик заземлённого контекста» между фактами по просрочке и генератором претензии. Весь процесс одной претензии (≤8 LLM-вызовов, ТЗ Q27):

```
Триггер просрочки (payment_days vs 1С)
        │
        ▼
[1] Классификация типа претензии        ← LLM #1
        │  claim_type ∈ {просрочка оплаты, недоставка,
        │                повреждение груза, простой ТС, недогруз}
        ▼
[2] RAG-Retrieve  ◀── ЭТОТ ДОКУМЕНТ
        │  вход:  claim_type + client_id + trip_context
        │  выход: контекст из 3 коллекций + точные ссылки на пункты
        ▼
[3] Извлечение фактов из документов       ← LLM #2–3 (по RAG-чанкам)
        ▼
[4] Генерация черновика по шаблону        ← LLM #4–5
        ▼
[5] Guardrail-проверка (ссылки, суммы)    ← LLM #6–7 + rule-based
        ▼
   Юрист (human-in-the-loop)
```

RAG отвечает за шаг [2] и питает шаги [3]–[5]. Критично: **всё, на что ссылается претензия (пункт договора, статья закона, формулировка шаблона), должно физически присутствовать в retrieved-контексте** — иначе это галлюцинация и critical error (Q21).

## 2. Три коллекции vector store

Согласно Q14 — ровно три коллекции. Разделяем их, потому что у них разные стратегии чанкинга, разные фильтры и разная «свежесть».

### 2.1. `contracts` — договоры (источник истины по требованиям)
- **Источник:** DOCX/PDF договоров по контуру экспедитор↔клиент (MVP), позже перевозчик↔экспедитор.
- **Чанкинг:** структурный, по разделам и пунктам. Один чанк = один пункт/подпункт с сохранённым **номером пункта** и путём раздела.
- **Метаданные (payload):**
  | поле | пример | назначение |
  |---|---|---|
  | `client_id` | `X5`, `magnit`, `wb` | pre-filter по клиенту |
  | `contract_id` | `uuid` | связь с карточкой в БД |
  | `contract_number` | `ТЭУ-2024/13-05` | для формулы ссылки |
  | `contract_date` | `2024-05-13` | для формулы ссылки |
  | `contour` | `exp_client` / `carrier_exp` | параметризация контура (Q31) |
  | `contract_type` | `ТЭУ` / `перевозка` / `оферта` | выбор норм права (Q11) |
  | `section_path` | `4. Ответственность сторон` | навигация |
  | `clause_number` | `4.2.1` | **точная ссылка** (Q10) |
  | `clause_topic` | `неустойка` / `подсудность` / `срок оплаты` / `претензионный порядок` | целевой retrieve |
  | `is_current` | `true/false` | версии/редакции оферт |

### 2.2. `claim_templates` — шаблоны претензий (~15 шт, Q15)
- **Источник:** Word-шаблоны юр.отдела Marshall MTL.
- **Чанкинг:** шаблон целиком как один документ + отдельные чанки по блокам (шапка, требования, расчёт, приложения) для точечной вставки.
- **Метаданные:** `template_id`, `claim_type`, `client_id` (nullable — есть спец-шаблоны X5/Магнит/WB), `expeditor_id`, `is_default`, `outcome_stats` (paid_voluntarily/…, Q5 — только для аналитики, не для retrieval-ранжирования).
- **Логика выбора (Q16), приоритет:** `client_id` → `claim_type` → дефолт экспедитора. Реализуется как **детерминированный selector по метаданным, а не по векторному сходству** (шаблон нельзя «угадывать» эмбеддингом).

### 2.3. `legal_norms` — нормативная база (Q11, Q14)
- **Источник:** ГК РФ (ст. 309, 310, 314, 395, 801), УАТ (ст. 28), АПК (ч.5 ст. 4). Ручной, выверенный корпус — **не парсим из интернета**, чтобы не тащить неактуальные редакции.
- **Чанкинг:** одна статья (или часть статьи) = один чанк. Точная цитата важнее полноты.
- **Метаданные:** `code` (ГК/УАТ/АПК), `article`, `part`, `topic` (`неустойка` / `проценты` / `экспедиция` / `претензионный_порядок`), `applies_to_contract_type`, `edition_date`.
- **Приоритет применения (Q11–Q12)** зашит в selector, не в LLM:
  1. договорная неустойка (из `contracts`, если есть `clause_topic=неустойка`);
  2. ст. 309/310/314 ГК — общие;
  3. ст. 395 ГК — **только если** в договоре нет условия о неустойке (одновременное применение запрещено, п.4 ст.395);
  4. ст. 28 УАТ — договоры перевозки;
  5. ст. 801 ГК — ТЭУ.

## 3. Пайплайн индексации (ingestion)

```
DOCX/PDF/XLSX/JSON
   │
   ▼ (1) Extract     unstructured / python-docx / pdfplumber / openpyxl
   ▼ (2) Normalize   единый internal-JSON: {doc_type, raw_text, structure[]}
   ▼ (3) PII-mask    ФИО→<PERSON_N>, паспорт→<PASSPORT>, тел→<PHONE_N>,
   │                 счёт/карта→<BANK_ACC>, адрес→<ADDRESS_N>
   │                 (ИНН/ОГРН/юрлицо/суммы НЕ маскируем — Q9)
   │                 маппинг ↔ плейсхолдеры в отдельную шифрованную таблицу
   ▼ (4) Chunk        структурный сплиттер (см. §4)
   ▼ (5) Enrich       извлечение clause_number, clause_topic, section_path
   ▼ (6) Embed        GigaChat Embeddings API (батчами)
   ▼ (7) Upsert       vector store + payload; idempotent по (contract_id, clause_number)
```

Особенности:
- **PII-маскирование выполняется ДО эмбеддинга и ДО любой отправки в GigaChat** (Q7–Q9). В индекс попадает уже маскированный текст; реальные значения возвращаются reverse-mapping'ом в защищённом контуре при финальной сборке претензии.
- **Excel (выгрузки 1С по платежам)** и **JSON (рейсы/заявки из БД)** — это структурированные факты, а не текст для семантического поиска. Их **не векторизуем**, а кладём в реляционную БД и достаём точными запросами по `trip_id`/`client_id`. RAG отвечает только за юридический текст (договоры, шаблоны, нормы).
- **Версионирование оферт:** редакции `usloviya-perevozki-*` имеют даты — храним `edition_date`, для расчёта берём редакцию, действовавшую на дату спорного рейса.
- **Идемпотентность:** повторная загрузка договора не плодит дубли (upsert по `contract_id + clause_number`).

## 4. Стратегия чанкинга (самое важное для точности)

Наивный размерный сплиттер (по 512 токенов) **ломает нумерацию пунктов** и приводит к неверным ссылкам → critical error. Поэтому:

- **Договоры — иерархический structural chunking:** парсим нумерацию (`4`, `4.2`, `4.2.1`), каждый лист-пункт = чанк. В метаданные пишем точный `clause_number` и `section_path`. Слишком короткие пункты склеиваем с родителем (parent-child), но `clause_number` сохраняем массивом, чтобы ссылка оставалась точной.
- **Контекстное окно чанка:** к тексту пункта в эмбеддинг добавляем «хлебные крошки» (`Раздел 4. Ответственность → п.4.2 Неустойка → 4.2.1 …») — улучшает семантику без потери точности ссылки.
- **Нормы:** одна статья = один чанк, без разбиения (короткие).
- **Шаблоны:** блочный чанкинг (шапка / основание / требования / расчёт / приложения).

Правило ссылки формируется детерминированно из метаданных, а не генерацией:
`«п. {clause_number} {section_path?} Договора № {contract_number} от {contract_date}»`.
Если для требуемого `clause_topic` (напр. `неустойка`) чанк в договоре **не найден** → RAG возвращает `flag: manual_review` и генератор НЕ выдумывает пункт (Q10, Q21).

## 5. Retrieval — как отдаём контекст в генератор

Вход в retriever: `{claim_type, client_id, contour, trip_context, contract_id}`.

### 5.1. Маршрутизация (metadata pre-filter, потом вектор)
1. **`contracts`:** hard-filter `contract_id` (или `client_id + contour + is_current`) → внутри достаём целевые пункты по `clause_topic` (`неустойка`, `срок оплаты`, `подсудность`, `претензионный_порядок`) + семантический top-K по тексту требования.
2. **`claim_templates`:** детерминированный selector (клиент → тип → дефолт), **1 шаблон**, не векторный поиск.
3. **`legal_norms`:** selector по правилам приоритета §2.3 + семантический добор по `topic` и `contract_type`.

### 5.2. Hybrid search + rerank
- **Dense** (GigaChat embeddings) **+ sparse/BM25** по русскому юридическому тексту (термины «неустойка», «пени», номера статей — точное совпадение критично).
- **Reranker** (cross-encoder или лёгкий LLM-rerank) поверх top-N → top-K, чтобы в 32K-бюджет попадали только релевантные пункты.
- **Token budget guard:** суммарный retrieved-контекст жёстко режется под лимит 32K (Q25) с приоритетом: договорные пункты > нормы > справочный текст шаблона. Учёт токенов до отправки.

### 5.3. Что возвращает RAG (контракт-объект для генератора)
```json
{
  "claim_type": "просрочка оплаты",
  "template": { "template_id": "...", "source": "client-specific|type|default" },
  "contract_clauses": [
    { "clause_number": "4.2.1", "topic": "неустойка",
      "text": "...", "citation": "п. 4.2.1 Договора № ТЭУ-2024/13-05 от 13.05.2024" }
  ],
  "legal_norms": [
    { "code": "ГК РФ", "article": "395", "reason": "в договоре нет условия о неустойке" }
  ],
  "penalty_basis": "contract | art_395",   // взаимоисключающе (п.4 ст.395)
  "jurisdiction": { "court": "...", "source_clause": "8.3" },
  "claim_deadline_days": 30,               // из договора или fallback ч.5 ст.4 АПК
  "flags": ["manual_review:penalty_clause_not_found"?]
}
```
Этот объект — единственный «мостик» из RAG в генератор. Он самодостаточен: каждая цитата уже собрана, каждый флаг проставлен.

## 6. Технологический стек (рекомендация)

| Слой | Выбор (MVP) | Обоснование |
|---|---|---|
| LLM / Embeddings | **GigaChat Pro + GigaChat Embeddings** | требование кейса; лимит 32K |
| Vector store | **pgvector** (в существующем PostgreSQL) | стек CargoTech уже на PostgreSQL; минус один сервис; богатый metadata-фильтр через SQL |
| Альтернатива | Qdrant | если нужен продвинутый payload-filter/HNSW-тюнинг под масштаб v2 |
| Sparse/BM25 | PostgreSQL FTS (`tsvector`, русская конфигурация) | нативно, без доп. инфры |
| Парсинг | `python-docx`, `pdfplumber`, `openpyxl`, `unstructured` | форматы MVP (Q6), без OCR |
| Оркестрация | тонкий свой слой поверх GigaChat SDK | контроль числа вызовов (≤8) и токенов |
| PII-маскирование | свой rule-based + NER (Natasha/SpaCy ru) на backend | до отправки в LLM (Q8) |

> Рекомендация: **pgvector**, чтобы не плодить инфраструктуру на хакатоне и держать источник истины и вектора рядом. Qdrant — если решим выделять RAG в отдельный сервис под масштабирование на Nikotrans (Q без номера — «подготовиться к масштабированию»).

## 7. Оценка качества RAG (отдельно от качества претензии)

Кейс оценивает финальную претензию (Q19–20), но RAG нужно мерить изолированно, чтобы отлаживать:

- **Retrieval-метрики** на 5 публичных эталонных кейсах (Q20):
  - `context_recall` — попал ли в контекст нужный пункт договора/нужная статья;
  - `citation_accuracy` — совпадает ли сгенерированная ссылка «п. X.Y» с реально существующим пунктом (прямая защита от critical error Q21);
  - `penalty_basis_correctness` — верно ли выбрано «договор vs ст.395» (Q12);
  - `template_selection_accuracy` — верный ли шаблон по приоритету (Q16).
- **Faithfulness / no-hallucination:** доля утверждений в черновике, подтверждённых retrieved-контекстом (RAGAS-подобно). Целевой ноль по «ссылка на несуществующий пункт».
- **Token/cost budget:** ср. токенов и стоимость retrieve-контекста → вклад в цель ≤50 ₽/претензию (Q26).

## 9. Пошаговый план реализации

**Этап 0. Подготовка корпуса (0.5–1 день)**
1. Разобрать предоставленный dataset (после NDA): договоры по 2 контурам, ~15 шаблонов, нормы.
2. Собрать выверенный `legal_norms` вручную (ГК/УАТ/АПК — нужные статьи), зафиксировать редакции.

**Этап 1. Ingestion-пайплайн (1.5–2 дня)**
3. Парсеры DOCX/PDF/XLSX/JSON → internal-JSON.
4. Модуль PII-маскирования (rule-based + ru-NER) + шифрованная таблица маппинга.
5. Структурный чанкер договоров с извлечением `clause_number`/`section_path`/`clause_topic`.
6. Эмбеддинг (GigaChat) + upsert в pgvector, idempotent.

**Этап 2. Retrieval-слой (1.5–2 дня)**
7. Metadata pre-filter + hybrid (dense+BM25) + reranker.
8. Детерминированные selector'ы: шаблон (Q16), нормы права (Q11–12), подсудность/сроки (Q13).
9. Сборка контракт-объекта §5.3 + token budget guard + флаги manual_review.

**Этап 3. Оценка (1 день)**
10. Прогон 5 публичных кейсов: context_recall, citation_accuracy, penalty_basis, template_selection.
11. Тюнинг: размер чанка, top-K, порог reranker, конфигурация FTS.

**Этап 4. Стыковка (0.5 дня)**
12. Отдать retriever как сервис/функцию генератору претензий; зафиксировать контракт §5.3.
13. Прокинуть флаги manual_review в guardrail-агент.

**Итого RAG-контур:** ~5–6.5 дней. Внешние зависимости: доступ к dataset (NDA) и ключ GigaChat.

## 10. Открытые вопросы (нужно решение до старта Этапа 1)

1. **Vector store:** pgvector (рекомендую) или Qdrant отдельным сервисом?
2. **Reranker:** cross-encoder локально (ru) или LLM-rerank через GigaChat (тратит бюджет вызовов из лимита ≤8)?
