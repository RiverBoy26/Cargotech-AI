# CargoTech AI — critical fixes before RAG validation

Дата: 2026-07-30

## Что исправлено

### 1. Изоляция договорного контекста

- `client_id` теперь обязателен при извлечении договорных чанков.
- Каждый запрос к `CONTRACT_CONTEXT` фильтруется одновременно по `contract_id` и `client_id`.
- Индексация договорного чанка без `client_id` отклоняется.

Это устраняет риск попадания условий договора другого клиента в претензию.

### 2. Полный текст нормативного контекста

`legal_context` теперь передаёт в промпт:

- `chunk_id`;
- `law_code`;
- `article`;
- `purpose`;
- полный текст нормы;
- citation;
- дату проверки;
- область применимости.

Модель обязана вернуть `chunk_id` использованной нормы. Guardrail проверяет соответствие `chunk_id`, закона и статьи.

### 3. Порог качества RAG

Добавлены отдельные настраиваемые `score_threshold`:

- договоры — `0.45`;
- нормы — `0.45`;
- шаблоны — `0.40`;
- примеры — `0.40`.

Порог передаётся непосредственно в Qdrant, а не применяется после выдачи.

### 4. Объединение RAG и входного контекста

Полученный RAG-контекст больше не затирает переданный backend-контекст. Источники объединяются с дедупликацией по `chunk_id` и стабильным резервным ключам; при конфликте приоритет имеет явно переданный доверенный контекст. Если Qdrant/embeddings временно недоступны, pipeline использует переданный `contract_context`; без такого fallback вызов прекращается до обращения к LLM.

### 5. Проверка фактов в тексте претензии

Guardrails дополнительно проверяют сам `claim_text`:

- стороны и ИНН;
- отсутствие посторонних ИНН;
- номер и дату договора;
- маршрут;
- номера и даты акта, ТТН, счёта и заявки;
- срок оплаты или дату/место погрузки;
- наличие всех сумм backend-расчёта;
- отсутствие денежных сумм, не переданных backend;
- обоснованность списка приложений.

Любой неизвестный ИНН, чужая сумма или несогласованная ссылка приводит к `BLOCK`.

### 6. Ужесточение бизнес-правил

- `PARTIALLY_PAID` разрешён для претензии по фактическому остатку долга.
- Неподтверждённый диспетчером `LOADING_FAILURE` теперь блокируется.
- Проверяется равенство `total_amount = principal_debt + penalty_amount`.
- `manual_review_required = true` остаётся обязательным.

### 7. Безопасные LLM-логи

Перед сохранением preview маскируются:

- стороны, ИНН и адреса;
- телефоны и email;
- паспортные и банковские данные;
- госномера;
- суммы, ставки и формулы;
- токены авторизации.

Текст ответа модели больше не добавляется в сообщение parser exception.

### 8. Безопасный API-ответ

Из `GenerateClaimPipelineResponse` удалены:

- `prompt_messages`;
- `raw_model_response`.

Добавлены:

- `request_id` для трассировки;
- `token_usage`.

Backend/frontend, использующие удалённые поля, необходимо синхронизировать.

### 9. Диагностические эндпоинты

Auth-check, тестовые GigaChat/embedding, parser/guardrail preview, RAG demo seed, Qdrant admin и просмотр LLM-логов отключены по умолчанию.

Для локального демонстрационного стенда:

```text
AI_DIAGNOSTICS_ENDPOINTS_ENABLED=true
```

На публичном стенде оставлять `false`.

### 10. Полный pipeline документов LOADING_FAILURE

Добавлены настоящие generation pipelines:

```text
POST /api/ai/documents/loading-failure/notification/generate
POST /api/ai/documents/loading-failure/act/generate
```

Оба выполняют:

```text
RAG → prompt → GigaChat → parser → document guardrails → safe response
```

Guardrails запрещают в уведомлении и акте:

- суммы и денежные требования;
- судебные формулировки;
- чужие стороны и ИНН;
- вымышленные пункты договора;
- неподтверждённые приложения.

### 11. Защита индексации

Индексация отклоняет текст с вероятными немаскированными:

- телефонами;
- email;
- паспортами;
- банковскими счетами и картами;
- госномерами транспортных средств;
- повреждённой UTF-8-кодировкой.

Числовой `client_id` и номер договора не трактуются как ПДн: проверяется содержимое индексируемого документа, а не технические идентификаторы.

### 12. Автоматические тесты

Добавлены тесты:

- tenant isolation RAG;
- маскирование логов;
- фактологические guardrails претензий;
- guardrails уведомления/акта;
- валидация RAG-индексации.

## Новые настройки

```text
GIGACHAT_MAX_TOKENS=2000
RAG_CONTRACT_MIN_SCORE=0.45
RAG_LEGAL_MIN_SCORE=0.45
RAG_TEMPLATE_MIN_SCORE=0.40
RAG_EXAMPLE_MIN_SCORE=0.40
AI_DIAGNOSTICS_ENDPOINTS_ENABLED=false
```

## Обязательная миграция перед запуском

1. Все договорные чанки должны содержать корректные `client_id` и `contract_id`.
2. Старые договорные чанки без `client_id` нужно удалить или переиндексировать.
3. Frontend/backend не должны ожидать `prompt_messages` и `raw_model_response` в pipeline response.
4. Для старого demo-скрипта локально включить `AI_DIAGNOSTICS_ENDPOINTS_ENABLED=true`.
5. После запуска на реальном корпусе откалибровать четыре RAG-порога по Recall@K и числу пустых/ошибочных выдач.

## Проверка

```powershell
mvn clean test
```

Затем запустить приложение и существующий demo suite с включёнными диагностическими эндпоинтами.

## Что осознанно отложено до этапа данных

- hybrid BM25/vector retrieval;
- reranker;
- калибровка score threshold;
- обязательные поля `source_version`, `valid_from`, `valid_to`, `source_hash`;
- юридическая экспертная оценка сгенерированных документов.
